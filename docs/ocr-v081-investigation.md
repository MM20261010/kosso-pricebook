## 2. 前回の試験で足りなかった条件

前回の再現データは管理行が日付より**下**にあり、読める管理ラベルとASCII数字が連結していた。小計は既知の「小汁/小訐/小言十」と「8点」がまとまった文字列だった。v0.8は主にその文字パターンに依存し、日付より上の領域や、金額列・点数・後続税額を組み合わせて未知の小計を保留する処理がなかった。

今回の固定架空データは、同じ6商品・位置・金額・単価×数量を保ち、要因を分けて変更する。実店舗名・実管理番号・実OCRの転記は使わない。管理ラベルのI/O/0等の文字崩れ、小計の分割領域と「点→占」を使い、出力し得る文字かを同梱PP-OCRv5辞書でも確認した。辞書にない「奌」や不可視形式文字は直接Paddle出力の再現要因から除いた。不可視文字の表示・正規化は、編集テキスト等の副経路の防御に留め、実機失敗原因とは主張しない。

| 入力条件 | v0.8（旧ソース） | 新処理（ソース） |
|---|---:|---:|
| 前回の再現条件 | 6 | 6 |
| 管理行を日付の上へ移すだけ | 6 | 6 |

## 3. 分類処理の変更

- 日付を位置の基準にし、その上の価格らしい行を管理/保留へ分離。日付が先頭6行にあることは要求せず、既に商品ブロックがある場合や下部の日付を管理ヘッダーの基準にしない。
- 番号の数字を正しく読めたかに依存せず、店舗/レジ/担当/取引など複数の弱い管理信号も利用する。確信できない管理らしい行は詳細に残し、商品にしない。
- 未知の小計は、点数らしい表記・商品列と合う金額位置・明細合算・後続の税/合計/支払を組み合わせて**小計候補**にする。見出しは未確定のまま。金額不一致や座標不足なら集計らしい行として保留し、金額を補完しない。
- 商品の後の金額付き税行も商品明細の終端として扱う。税/合計以降の未知行は商品へ追加しない。価格区分の宣言だけでは明細を終えない。
- 数量のロジックと正常な単価×数量対応、DB/JSON形式、同梱OCRエンジンは維持。全体点数から個別数量を推測しない。

## 4. 端末内の分類理由

v0.8.1 / versionCode **9**。`assets/build-info.json` とBuildConfigに、ソースコミット・解析リビジョン・未コミット変更の有無を埋め込む。CIは埋め込みコミットと `GITHUB_SHA` が一致し、未コミット変更がないことを検証する。ローカルの未コミット試作をコミット済みソースと誤表示しない。

「管理」で版とソースを確認できる。「記録」→「レシート詳細・集計・認識テキスト」→「ビルド・領域別の分類理由（端末内だけ）」で次を確認する。

- `POSITIONED` / `TEXT` の解析経路と、読み取り・原文再解析・復帰の区別。
- 検出領域番号、復元行、位置、分類、理由コード、商品候補との対応。日付基準の有無・日付より上か・管理信号数・点数らしい表記・金額列・明細計一致・後続集計の有無も記録し、分類に至らなかった条件を原文なしで確認できる。判定信号には実番号・金額・原文を含めない。
- 原文/正規化はさらに展開した場合だけ表示。データをログ・DB・JSON・ファイル・外部Intentへ出さない。診断画面はFLAG_SECUREで画面取得を抑止し、共有/送信機能を持たない。

| 主な理由 | 意味 |
|---|---|
| `PRE_DATE_HEADER_PRICE_HELD` | 早い日付より上の番号/金額らしい領域を商品にしない |
| `MULTIPLE_ADMIN_SIGNALS_HELD` | 複数の管理ラベルらしい信号から保留 |
| `SUBTOTAL_COLUMN_COUNT_SUM_FOOTER` | 点数・金額列・明細計・後続集計から小計候補 |
| `SUMMARY_LIKE_AMOUNT_MISMATCH_HELD` | 集計らしいが合算不一致。金額は確定しない |
| `SUMMARY_LIKE_NO_POSITION_HELD` | 座標がないため集計らしい行を保留 |
| `MONETARY_TAX_FOOTER_BOUNDARY` / `AFTER_SUMMARY_HELD` | 税/集計を境に商品候補生成を止める |
| `ITEM_POSITIONED_AMOUNT` | 位置付き処理で商品候補になった行。誤候補なら切り分け対象 |
| `UNIT_QUANTITY_AMOUNT_MISMATCH` | 別商品らしい数量を流用しない |

同じ文字列の「@245×2」が複数出ても、拒否した行を別商品の有効な数量行と誤って対応表示しないよう、実際の分岐と結び付け先を記録する。

## 5. 検証状態

Actionsは手動のみ。今回の手動実行では `compare_v08_apk=true` を指定し、期限内の元Artifactを取得。SHA-256とversionCode 8を確認した**元の署名付きv0.8 APK**を再署名/インストールせず、Android ARTのクラスパスで同一の固定架空入力に通す。新APKにも同じプローブを通す。購入DB・実レシートを読む経路はない。比較を指定しない将来の手動ビルドは、旧Artifactの期限に依存せず新APKの検証を実行できる。

同じ写真でPaddle読み取り直後の版番号9・埋め込みコミット・`POSITIONED` を確認し、候補数と誤候補2行の分類理由を端末内で調べる。実画像・OCR全文・番号・原文を送る必要はない。報告する場合は**候補数、解析経路、理由コード、日付より上か下か**だけでよい。
