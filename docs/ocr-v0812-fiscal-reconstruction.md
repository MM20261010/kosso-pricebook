# v0.8.12：元領域を保持した集計再構成

基盤：PR #10の88bd5d3（v0.8.11実装1bd2af6以後は文書のみ）。PRベース`fix/ocr-classification-gates-v084`のb4e92bcは作業ブランチの祖先で、既存差分を保持している。同じ作業ブランチ/Draft PRを使い、mainは変更・マージしない。
[本人の最新匿名診断](https://github.com/MM20261010/kosso-pricebook/issues/11#issuecomment-6621471591)を読んで継続した。実画像・OCR全文・購入情報は受領していない。

## 確認済みと仮説

実機で6商品・両数量2・暫定1点・小計分離を維持した一方、税率行が`ROLES_UNKNOWN / NONE / UNKNOWN`、一部税行が`GRAMMAR_REJECTED`、一部集計領域が`OVERLAPPING_REGIONS_HELD`で止まることは確認済み。
重なった行が最終合計そのものか、具体的な見出しの字形・値・配置は未確認。以下の再現は同じ停止経路の架空データであり、本人写真の直接原因を確定したものではない。

コードで確認した点：`ReceiptLayout.rows()`は重なりを商品へ混ぜないため行を分離・保留し、`productText()`も曖昧行を整形しない。この安全条件は変更しない。
従来は同じ保留状態から集計を再検討する経路がなく、見出しと金額が別々に保留された場合は総額候補にならない。税も厳密な文法から見出しが外れると、後続の単一税率・数値だけでは役割を決められない。

## 実装範囲

- `ReceiptFiscalRecovery`を認識後の追加解釈として導入。商品解析を終えてから、最後の商品以降の小計/税/合計領域を対象にする。既存の商品、元行、領域文字列・座標・source IDを削除・置換しない。再構成した解釈を別の端末内診断行として追加する。
- 同じ文字列と十分重なる座標を持つ領域は、元の両領域を残した「同じ観測の解釈」として扱う。異なる数字の重なりは一つに選ばず保留する。商品用の行結合・コード除去・数量関連付けの基準は緩めない。
- 既知の合計見出しの分割文字と、同じ高さまたは限定距離の右側金額を対応付ける。別の見出し、決済、値引き、返品等が競合する結合は拒否する。税額が未取得でも、独立して読めた合計の確認候補は残す。複数金額は候補一覧で示し、便利な一額を選ばない。日報・支払・預り・釣銭は転用しない。
- 税表の列見出し・内訳/区分等のラッパーを、数字の文法とは別に解釈する。明示された順序、税率、点数、対象額、税額、方式を保持する。連続セルは最大3セル、記号だけのノイズは2行まで。離れた行や不明な文字列を越えて役割を無制限に継承しない。
- 再構成した税率別値・合算は不確実な候補。既存の確かな値を上書き・降格せず、矛盾は要確認へ。印字のない税率・数量・総額・丸め方を補わず、商品別税込単価へ税額を配分しない。小計は従来の確認欄を維持する。

### 実画像OCRで見つかった差

新しい架空画像で、実モデルが「額」を「额」と返し、税見出しが厳密な文法から外れることを確認した。集計見出しの解釈だけでこの字形を扱い、商品名の文字列は変更しない。
また、対象額と税額の間の空白が消えた単一の数字列を観測した。観測済みの列順・方式・税率があり、桁の分割と税計算（切捨て/切上げの範囲）が一意に整合する場合だけ、確認待ちの分割候補を作る。
別々に観測した数字を連結して都合のよい金額を作ることは禁止し、逆方向試験を追加した。方式不明、列役割不明、壊れた数字、上限超過、複数解釈では確定しない。

### 残る画像OCRの失敗

同じ架空の分割行レイアウトを縦長1800pxにしたストレス画像では、旧新版とも商品と数量行の領域干渉、小計混入が残った。今回の商品領域安全条件は緩めず、改善したとは扱わない。
この画像も捨てずに試験APKへ残す。ただしAndroidでは「未確認商品の自動選択/保存なし」等の安全性と両OCRの実行・画像不変だけを検査し、認識精度合格の枚数には含めない。特定の高さ全般に問題があると断定するものでもない。

## 短い匿名診断

上部の既存コピー操作を`SCOPE=FISCAL_ONLY`に変更。商品候補の詳細を除き、集計の領域状態、結合、見出し、金額抽出、税役割、候補化/保留の理由を固定enumで出す。
同じ状態を重複して出さず、最大12状態・約7,000字。上限では`REPORT=TRUNCATED`を明記する。原文・名称・店舗・日時・金額・番号・座標・行IDは含めない。
コピーは明示操作のみ。sensitiveクリップ指定を維持し、ログ・自動保存・送信は追加しない。従来の全文診断は端末内詳細に残すが、本人へ再提出を求めない。

## 検証と三原則

- JVM回帰は従来948＋集計再構成74＝1,022項目。文字列と合成座標、既存6/20/50商品、数量/例外、一括確認・保存拒否、集計再構成の20/50商品を含む。assertion数であり独立したレシート枚数ではない。
- 新規標準画像2枚は実C++/ncnn FP32で通信syscall禁止下のホスト推論を実施。文字列だけでなく実検出領域→`ReceiptLayout`→`ReceiptParser`を通した。PNG/フォントのSHA-256を試験manifestに記録する。
- Android試験APKは既存11枚＋新規2枚＋既知制限1枚。13枚のPaddle認識/解析の検査と、1枚の未解決ストレス試験を区別する。Tesseractは同じ画素で実行と画素不変を検査し、税表の正答率合格とはしない。
- アプリ/試験APKのローカルビルド成功。Lintエラー0・既存警告6、署名・Manifest・英日/Paddle資産ハッシュ・固定出所・ライセンス同梱・3 ABIの防御設定検査が合格。配布用はクリーンな実装コミットのActions生成APKを使う。
- DBスキーマ2、v1/v2 JSON、依存ライブラリ、モデル/ネイティブコード、Manifest/公開コンポーネントは変更しない。端末内OCR、INTERNETなし、自動バックアップ無効、モデル同梱、外部収集なし、追加費用0円、手動CIを維持する。
- 再構成は既存の文字/行/金額制限内。税見出し100字、領域解釈240字、数値分割14桁・各100万円、追加解釈40件等で制限する。原本や購入情報をGitHub/CIへ入れない。
